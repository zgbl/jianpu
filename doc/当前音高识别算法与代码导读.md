# 当前音高识别算法与关键代码导读

本文按当前工作区代码记录识别流程，供排查“原始音高已经错了”“分段把滑音当音符”以及“音高转成简谱后看起来错了”等不同问题。代码仍在迭代；请以本地正在运行的服务所加载版本为准。

## 先区分三件事

1. **基频测量**：从人声波形逐帧估计频率 `f0`，再换算成绝对 MIDI 半音值。这一步由 librosa 的 pYIN 完成。
2. **音符事件解释**：将连续帧整理成带起止时间和音高的音符。页面当前默认选“稳定音高核心 v3”；“旧分段 v2”可作基线。
3. **简谱排版**：将 MIDI 音高按 Do 映射成数字，并按节奏格放进小节。Do 只改变数字表示；音高和相邻音程是否正确，应先在绝对 MIDI / 未量化试听层判断。

这三个环节会产生不同的错误。若 `pitch-observations.json` 中稳定的 MIDI 已偏半音，改分段无法修复测量；若观测曲线稳定而事件被拆错，才主要是分段问题；若“未量化旋律 MIDI”听起来正确而纸面不正确，则继续查节奏格和谱面转换。

## 处理流程

```text
音频文件
  ├─ 原曲模式：解码 → Demucs 分离 vocals → 取人声单声道
  └─ 清唱/独奏模式：解码 → 直接使用输入
       ↓
重采样为 16 kHz
       ↓
librosa.pyin：逐帧 f0、是否有声、voiced_prob
       ├─ pYIN 原始连续观测 / 音高轨迹
       ↓
v2 整数分段，或 v3 稳定核心分段
       ↓
识别事件（绝对 MIDI + 秒数）
       ↓
按 Do 映射简谱数字，再由节奏网格量化和排小节
```

前奏器乐识别走 `audio/intro-melody.py` 的单独流程：`librosa.piptrack` 取候选峰值后选最大峰，并调用 v2 `pitch_events`。它不使用此处的 pYIN/v3 人声流程。

## A. 音源和前处理

入口是 [audio/transcribe.py](/Users/tuxy/Codes/Github3/Music-JianPu/audio/transcribe.py:61)。ffmpeg 将所选时间段解码成 44.1 kHz 双声道 WAV；时长至少 0.5 秒，最多约 10 分钟。

原曲模式调用 [audio/separate.py](/Users/tuxy/Codes/Github3/Music-JianPu/audio/separate.py:14)，Demucs `htdemucs` 或 `htdemucs_6s` 在 CPU 上分离声部。所有声部共用同一个峰值增益，不单独归一化。随后只对 `vocals.wav` 识别人声旋律，不直接对混合原曲估计主唱音高。分离残留的伴奏、和声、合唱仍可能影响单音高估计；Demucs 声部名不能证明内容完全纯净。

清唱/独奏模式直接使用输入，写出 `vocals.wav`。当前这段代码的 `vocal / max(1, peak)` 会在峰值超过 1 时衰减，峰值低于 1 时不放大。

## B. 逐帧基频测量：pYIN

核心代码在 `audio/transcribe.py` 的 `run()`：

```python
sample_rate, hop = 16000, 256
mono = librosa.resample(vocal.mean(axis=1), orig_sr=sr, target_sr=sample_rate)
f0, voiced, probs = librosa.pyin(
    mono, fmin=65.4, fmax=1046.5, sr=sample_rate,
    frame_length=2048, hop_length=hop, fill_na=None
)
```

- `f0` 是每帧估计的频率（Hz）；有限正数可换算为 MIDI：`69 + 12 × log2(f0 / 440)`。这是绝对半音值，还没有转成 Do 数字，也没有吸附到调式音阶。
- `voiced` 表示 pYIN 判定该帧有声；`probs` 是 `voiced_prob`（有声概率），**不是“此音高正确”的概率**。代码中的旧字段 `confidence` 容易让人误读。
- hop 为 256 / 16000 = **16 ms**；2048 样本分析窗为 **128 ms**。librosa 默认居中分析，边缘采用常量填充。帧中心时间不是歌手起唱边界；长窗也会横跨快速音符边界。
- pYIN 搜索范围约 MIDI 36 至 84（C2 至 C6）。范围外的低音/高音不能按正常音高可靠识别。
- 当前没有第二个独立 f0 检测器，没有周期性/谐波一致性联合评分，没有整体调律偏移估计。`pitchReliability`、`sourceReliability`、`periodicity` 在 v3 事件中是 `null`。

后续先看 **pYIN 连续曲线是否测对**。若稳定长音的 `midi` 已与人声实际基音不符，v3 的音符分段无从恢复真值；此时需查声部分离、八度/谐波误判、f0 检测或音域，而不是先调乐谱 Do。

## C. 帧筛选与时间序列缓存

能量使用同一个 16 ms hop，但 1024 样本窗口（64 ms）：

```python
rms = librosa.feature.rms(y=mono, frame_length=1024, hop_length=hop)[0]
voiced &= rms[:len(voiced)] >= max(.0008, float(np.max(rms)) * .025)
```

原曲模式还要求人声 RMS / 原曲 RMS ≥ `.04`。此门槛意在压低伴奏残留，但弱唱、尾音或某些分离结果可能因此被屏蔽。pYIN 的 128 ms 音高窗和 RMS 的 64 ms 音量窗支持范围不同，尽管时间中心都按 hop 排列。

v2 使用以上**已经被能量和声源比筛过的** `voiced`。v3 另外保留原始 `raw_voiced` 和概率，在解码器内部使用概率与能量门槛；但当前解码器没有使用传入的 `voiced` 布尔参数（见下文问题清单）。原曲模式会把人声/原曲比例低于 `.04` 的帧的 v3 概率置零。

`pitch-observations.json` 每帧包含片段相对时间、连续 MIDI、原始 voiced、v2 eligibility、RMS、`voicingProbability`、兼容旧名 `confidence` 和选定分段算法的 `cleanedMidi`。分析元数据记录 librosa 版本、采样率、hop、窗长、时间原点、片段开始时间和人声音频 SHA-256。`pitchReliability`、`sourceReliability` 当前明确为空，不能从缓存字段推断测音正确率。

注意页面的 `pitchTrack` 并非全部原始 pYIN 观测：它每隔 3 帧抽样，并使用已经经过能量/混合音比例筛选的 `voiced`。查看未经该筛选的帧，应使用 `pitch-observations.json`。

## D. v2 旧事件算法

代码：[audio/pitch-segmentation.py](/Users/tuxy/Codes/Github3/Music-JianPu/audio/pitch-segmentation.py:15)。顺序是：

1. 只保留传入 `voiced` 且 f0 有限正值的帧，将 f0 换成浮点 MIDI。
2. `voiced_prob ≥ .35` 定义候选连续段；一段至少有一帧 `≥ .65`，然后**逐帧 `np.rint()` 到整数半音**。
3. 整数音段若无任何 `≥ .65` 帧就清掉。
4. 两侧同音包住的短异音段满足时长/音高条件时，改成两侧的音。两侧同音间 ≤96 ms 的空档，若 RMS 未明显降低则补成原音。
5. 少于 75 ms 的音段直接丢弃。同音段内只有 onset 同时有足够能量下降才切分重唱。

这意味着滑音在“音符解释”之前已经被整数取整；一条滑音跨过多个半音阈值时，会先出现多个整数片段。后续局部修补只合并特定短片段，无法可靠判断某个短半音平台是实际音符还是滑音经过音。

## E. v3 稳定核心解码器（实验）

代码：[audio/stable-pitch.py](/Users/tuxy/Codes/Github3/Music-JianPu/audio/stable-pitch.py:26)，UI 默认选中；可选择 v2 对照。当前是实验性启发式，并非方案中完整的 HSMM 或已用真实歌声数据调好的模型。

配置默认值均写在 `DEFAULTS`：

| 参数 | 当前值 | 代码用途 |
| --- | ---: | --- |
| 短/中/振音上下文 | 48 / 80 / 208 ms | 多尺度观察候选稳定帧 |
| 核心 IQR 上限 | 0.32 MIDI | 局部音高四分位范围 |
| 局部漂移上限 | 0.22 MIDI | 窗口前/后三分位中值差 |
| 核心拆分容差 | 0.45 MIDI | 按浮点趋势拆出新核心 |
| 最短核心 | 48 ms | 稳定候选最短长度 |
| 延续/种子 voiced_prob | 0.35 / 0.65 | 连续观测资格与可靠音岛条件 |
| 可连接的观测空档 | 96 ms | 还须端点相近、RMS 持续 |
| 合并代价参数 | 0.7，残差系数 8 | 核心组动态规划 |
| 重起音能量比 | 0.65 | onset 附近能量下降判定 |

以上都是当前源码数值，不是从歌曲验证集标定出来的门槛。

解码步骤：

1. 将 pYIN f0 转成**浮点 MIDI**；候选帧须 f0 有限为正、`voiced_prob ≥ .35`、RMS 高于 `max(.0008, 全段最大 RMS × .025)`。
2. 相邻候选帧之间的无效空档若 ≤96 ms、端点音高差 <0.5 半音，且空档 RMS 不低于边缘较低 RMS 的45%，只连接外层区间。空档帧仍不生成 f0。
3. 每个候选窗比较浮点 MIDI 的 IQR、前后三分位漂移。长窗允许至少两次方向反转且 IQR <1.25 半音的振音候选。核心帧组再按趋势与 0.45 半音阈值切开。
4. 核心要求至少48 ms，且其中至少一帧有声概率 ≥.65。候选核心序列再用动态规划分组：在中心范围差 ≤.45 半音时允许合并，成本为新组惩罚 `.7` 加加权中心残差 ×8；每次最多向前查看24个核心。
5. 相邻组之间在左核心之后遇到首个偏离其中心 >.45 半音的有效帧处切事件。组内同音重起音仍须 onset 和前后 RMS 凹口共同支持。
6. 只有确定事件所属稳定核心之后，才用该段观测的 voiced_prob 加权中值求浮点中心，再四舍五入为 MIDI 整数。没有稳定核心的整段滑动保留一个 `uncertain` 事件，不沿途逐半音拆开。
7. 保存事件表现起止、核心起止、浮点 `pitchCenterMidi`、`midi`、离散度、饰音类型及候选状态。缺少核心、靠近半音边界或离散度大于35 cents 时标记 uncertain。此时 `confidence` 设为0；其他事件的 `confidence` 仍取 voiced_prob 均值，不能当音高正确率。

### v3 当前尚未做到的事

- 没有完整联合解码起音、稳定段、滑出、真静默、观测缺失；目前仍是局部窗口找核心，再分组。
- 没有谱图谐波校验、独立音高模型、整体调律估计或调式吸附；当前 v3 也没有用 Do 定音。
- “滑音”标签根据核心前/后是否有偏离中心 >0.6 半音的观测生成，不是经过人工标注验证的演唱技法分类器。
- 同音重唱仍高度依赖 RMS 凹口，轻柔连唱可能被合并；辅音、气声、混响也可能改变 f0、概率或 RMS。
- 单调滑音在短窗内的漂移和 IQR 可能小于阈值；仍可能误判为稳定核心。2048 样本 pYIN 窗本身会平滑、跨越边界，也可能先把滑音测成不同轨迹。

## F. 当前工作区里应优先核查的代码细节

### 1. v3 收到了 `voiced`，但没有使用它

调用点传入 `raw_voiced`，函数签名也有 `voiced`：

```python
extract_events(f0, raw_voiced, decoder_probs, ...)
```

但 `stable-pitch.py` 的资格条件是：

```python
valid = finite & (prob >= cfg['continuationVoicing'])
```

这里没有与 `voiced` 布尔数组相与。pYIN 的 `voiced_prob` 通常与 voiced 状态相关，但源码不能保证二者完全等价；因此应核对“voiced=False、f0 有限、概率仍 ≥.35”的帧能否进入 v3 核心。此处是当前实现事实，不能仅凭合成测试通过就假定无影响。

### 2. pYIN 时间平滑和事件边界并非独立

128 ms f0 窗与 64 ms RMS 窗并不覆盖同一时间范围。短音上，f0 可能混合相邻音；能量 onset 是声学起音候选，也不一定等于有声元音/音高稳定核心的起点。缓存记了 `center=true`，但未将整段曲子的人工音符起点误差统计出来。

### 3. v3 不确定事件仍会进入谱面

`transcriptionToScore()` 用 `midi` 转 degree 时不因 `pitchStatus === 'uncertain'` 拒绝该音符。v3 uncertain 事件 `confidence=0`，但仍有有效 `midi/start/end`，所以会生成一个显示音符，并计入需核对数。置信度设0表示低信任提示，不是删除音符或回退旧谱。

### 4. 量化网格可能隐藏/丢弃相邻事件

当 `rhythmMode` 不是 legacy 时，`src/transcription-score.js` 把落在同一个 1/16 格的多个事件合成一个格，只留下按时长 × confidence 选出的事件，并显示过密候选数。它不会重新测 f0，却会让最终谱少掉短音；后续较早/较晚的取整和延音空档处理也改变谱面外观。对比音高模型时先听“未量化旋律 MIDI”，不要仅凭简谱反推 f0 对错。

### 5. 诊断信息在结果和谱面之间有损失

`melody-candidates-v3.json` 保留算法结果、核心诊断和 v2 对照；`pitch-observations.json` 保留帧曲线。转换后的 score 主要保存 MIDI/degree、置信显示值、时间和 `centsDeviation`，不把每个事件的核心区间、饰音和 `pitchStatus` 完整复制进 score。分析时应查看原始候选资产，不只看 `.jpu`。

## G. Do、半音关系与播放分别在哪一层

- pYIN 输出 MIDI；v2/v3 对 MIDI 音高分段。两者都不读取当前 `1=C` 等 Do，也不按某个大调的音阶吸附音高。
- `src/transcription-score.js` 将事件的绝对 MIDI 交给 `pitchToDegree(midi, selectedKey)` 生成简谱数字。Do 错会令显示数字对应错，但不会解释原始相邻 MIDI 差错。改 Do 后比较绝对 MIDI 和数字谱要分开。
- `suggestKey()` 是单独的调性建议统计，不是 pYIN 的音高算法；Do 分析/锚点也属于后续校准流程。
- **“未量化旋律 MIDI”** 使用候选事件的绝对 MIDI 和原始秒数；**“当前小节 MIDI”** 播放转成乐谱之后的音符，经过 Do 映射、节奏和小节网格。前者验证检测事件，后者验证谱面结果。

## H. 为什么现在的效果可能不好：逐层核查顺序

1. **先听原曲和 Demucs vocals**：若人声分离含强伴奏、和声或辅音破碎，pYIN 面对的就不是干净单旋律。
2. **看 `pitch-observations.json` 的原始浮点 MIDI**：找一段你确定的持续长音，检查中位音高是否正确、是否稳定；另查目标音域是否落在约 C2–C6 内，f0 是否出现八度跳变或断层。
3. **看同一片段 v2/v3 事件**：确认核心区间有没有落在稳定音上，滑音是否被拆成多个事件，短音/同音重唱是否保留。不要把声学 `voicingProbability` 当测音置信度。
4. **听未量化 MIDI**：跟人声比较真实绝对音高、相对音程和多余事件。若稳定长音也普遍错半音/全音，优先查 f0 检测、音源污染、调律/音域；若长音对、滑音碎，则查分段核心与边界。
5. **最后看纸面**：若未量化 MIDI 对而简谱不对，核查 Do、过密事件落同格、BPM/拍号和人工小节线。它们会影响数字/布局/时值，不应拿来判 pYIN 是否估对 Hz。

## I. 输出文件怎么读

每次识别运行目录中：

- `vocals.wav`：pYIN 的实际输入；先检查分离质量。
- `pitch-observations.json`：逐帧原始 MIDI、voiced、RMS、概率与处理元数据；用于判断 f0 层。
- `melody-candidates-v3.json`：选用算法的事件、核心与诊断，另含同次 pYIN 输入产生的 v2 基线。该文件名固定为 v3，即使选 v2；请看其 `selectedAlgorithm` 和 `version` 字段。
- `result.json`：页面显示的事件、节拍结果、警告和抽样 `pitchTrack`。
- 工程 score / `.jpu`：Do 和节奏映射后的谱面，不是 pYIN 原始结果。

缓存时间 `time` 和事件 `start/end` 均以**所选片段开头为0秒**；`clipStart` 才是原曲的开始秒数。核对原曲时换算 `原曲时间 = 片段相对时间 + clipStart`。

## J. 本文依据与尚未证明的内容

依据当前工作区 `audio/transcribe.py`、`audio/separate.py`、`audio/stable-pitch.py`、`audio/pitch-segmentation.py`、`src/transcription-score.js` 和 `src/transcribe-app.js`。代码设置的阈值不等于经过真人歌声验证过的参数。v3 合成轨迹及已知独奏样例通过，只能证明这些有限输入没有触发相应回归；《小酒窝》只读对照曾得到 v2 21 个事件、v3 22 个事件（其中3个不确定），没有人工逐音真值，因此不能证明真实歌曲准确率改善。

进一步研究可以先围绕一条已人工确认时间和绝对音高的 2–5 秒短句，逐帧比较 vocals、pYIN 浮点 MIDI、v2/v3 核心与事件，再分别改一个环节。没有人工标注真值前，不应宣称找到了某个错音的唯一原因。
