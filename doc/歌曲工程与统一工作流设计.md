# 歌曲工程与统一工作流设计

设计日期：2026-09-30。工程保存、导入/导出、统一状态、最近工程和修订版本已实现。具体操作见[歌曲工程使用说明](歌曲工程使用说明.md)。下文保留架构设计，并注明第一版限制。

## 1. 产品规则：一首歌是一个工程

工作流为：**新建/打开歌曲工程 → 导入音频 → 听歌识别 → 简谱编辑 → 保存工程 → 下次继续。**

识别和编辑在同一页面完成：识别成果自动进入可编辑谱面，共用工程名称、原曲、识别记录、当前乐谱和保存状态。`.jpu` 继续用于单独乐谱交换；保存完整工作必须使用工程保存。

改造前的问题：

- `src/transcribe-app.js` 的 `file`、`job`、`result`、`score` 只保存在页面内存，刷新后缺少恢复入口；原曲的 Blob URL 也不能保存成有效引用。
- `audio/api.mjs` 已把音频和结果写到 `.audio-jobs/<UUID>/`，但没有工程清单、最近工程入口和统一保存快照。
- 编辑器草稿存于浏览器 localStorage，识别页下载或写入的谱不能自动包含编辑器最新修订。
- 两个 iframe 目前主要交换乐谱路径，不共享一个有版本的工程状态。

仅增加“记住任务 ID”不能满足跨浏览器、移动文件或恢复完整工作。

## 2. 统一界面（2026-10-01 原地编辑版）

主页只加载一个工作视图，不再保留识别／编辑两个标签，也不再加载独立编辑 iframe。顶部工程栏固定显示新建、打开、保存、另存为及修订版本；视图上方试听原曲、人声和声部，下方是同一张可编辑 SVG 谱面。

`src/transcribe-app.js` 持有当前工作谱；`src/score-editor.js` 是原地编辑组件，处理音符输入／修改、时值／八度／附点、谱内歌词输入和拖动、小节线操作及撤销。识别生成的谱面立即交给这个组件。打开旧工程时，优先恢复已编辑的主谱；如果主谱为空，则直接将保存的识别结果生成可编辑谱面。

`src/barline-editing.js` 的插线、删线和移动线重新划分现有音符列表，保留 ID、原始时间、歌词和连线。人工划分允许暂时超拍、不满拍，谱面显示实际拍数；这与自动重算全曲是两个明确操作。重新识别或全曲重排生成新谱前，将人工谱保留到修订版本。

同一快照同时包含 `score`、`scoreBasedOn`、`transcribe` 和识别版本当前谱，不再通过“进入编辑器”交接文件路径。纯简谱工程也直接显示可写谱的空小节。旧 `editor.html` 链接重定向到主页。

## 3. 工程保存内容

| 内容 | 保存要求 | 打开后的行为 |
| --- | --- | --- |
| 原始音频 | 原始完整文件字节、文件名、类型和校验值 | 不再要求重新选择原曲，播放器可直接试听 |
| 处理片段 | 解码后的片段 WAV、原曲中的开始时间和长度 | 时间定位与识别输入保持一致 |
| 提取的人声 | 完整人声 WAV | 直接试听，不重新跑模型 |
| 原始识别结果 | 未量化音高轨迹、候选音符、置信信息、警告 | 支持查看轨迹和重新排谱 |
| 初始识别谱 | 本次识别/量化生成的 `.jpu` | 作为参考版本保留 |
| 当前修订谱 | 最新音符、歌词、连线、调号、拍号和播放速度 | 作为默认编辑和 MIDI 播放对象 |
| 识别及排谱参数 | 模型标识、输入类型、片段范围、BPM、调号、第一音拍位 | 恢复参数；不偷偷重算覆盖修订谱 |
| 工作位置 | 当前阶段、小节、选中音符、缩放、歌词段落、播放位置 | 恢复可继续工作的界面位置，播放保持暂停 |

保存文件本身，不能只保存用户原来电脑的绝对路径、临时 Blob URL 或 `.audio-jobs` 的 UUID。模型和 Python 环境不放进每个工程包；打开已有结果不应要求模型就绪，只有重新识别时才检查推理环境。

第一版打开工程后恢复最新修订和工作位置；内存撤销/重做栈重新开始。原始识别版本及每次重新识别的版本保留。后续若要求跨次打开撤销，增加持久编辑操作日志，避免把大量完整谱面快照塞入工程。

## 4. 文件格式：本机工作副本 + 可携带工程包

完整工程使用 `.jpp`（JianPu Project）作为项目内约定，内容是标准 ZIP。这是项目内扩展名，不代表已完成全网名称排他性核查。`.jpu` 仍是单独简谱 JSON。

本机工作目录与工程包使用同样的内部布局：

```text
歌曲.jpp（ZIP）
  manifest.json
  audio/
    original.mp3          # 原始扩展名按实际输入保留
  runs/
    <识别版本ID>/
      params.json
      clip.wav
      vocals.wav
      result.json
      recognized.jpu
  score/
    edited.jpu            # 人工修订后的当前主谱
  state/
    workspace.json        # 阶段、缩放、选区、试听位置
```

未识别时可以没有 `runs/`；清唱模式也记录输入模式；无音频工程可以没有 `audio/`。每份 manifest 的资产列表明确哪些文件存在、哪些阶段完成，不能依靠某个文件碰巧存在就认为任务成功。

manifest 的逻辑字段示意：

```json
{
  "format": "jianpu-project",
  "version": 1,
  "projectId": "工程UUID",
  "name": "曲名",
  "revision": 12,
  "source": { "path": "audio/original.mp3", "originalName": "原曲.mp3" },
  "activeRunId": "识别版本UUID",
  "score": { "path": "score/edited.jpu", "basedOnRunId": "识别版本UUID" },
  "workspace": "state/workspace.json",
  "assets": [
    { "path": "audio/original.mp3", "size": 123456, "sha256": "实际文件校验值" }
  ]
}
```

这是字段结构示意，实际清单由 `audio/project-store.mjs` 生成。资产路径均为工程内相对路径。每个 run 记录输入模式、时间范围、模型标识和方法；第一版尚未记录完整权重哈希及环境锁定信息。

MP3 基本已经压缩，归档时直接存储；WAV 按压缩策略处理。不能把音频转成 Base64 塞进 JSON 或 localStorage：文件更大、内存负担高，还容易触发容量限制。

## 5. “自动保存”和“保存工程”明确分开

本机服务维护 `.projects/<工程ID>/` 工作副本，新增 Git 忽略规则。导入原曲后即落盘；识别阶段完成的产物立即登记到该工程；编辑器操作按短延迟合并写入。最近工程列表从磁盘读取，不依赖浏览器草稿。

“保存工程”将一个完整、一致的当前版本打包成 `.jpp`，包含已经修订的谱和音频。支持系统保存选择器时写入用户指定文件；不支持时下载工程包，界面明确显示“已下载”。文件句柄不能保证跨浏览器重启保留，必要时重新选择保存位置，不能谎称已写回旧文件。

保存前先提交正在输入的歌词，收齐两个阶段的状态并等待写入确认；所有保存路径使用同一套 flush 流程。失败时保留待保存状态并报告，不能显示“已保存”。

本机自动保存不能被表述成已更新外部 `.jpp` 文件。工程切换前等待保存成功；手动新建/替换工程有未持久化修改时使用既有保存保护。关闭页时不依赖最后一刻异步请求：平时及时保存，尚有未确认写入时提示离开风险。

导入工程包时创建本机工作副本；同一工程 ID 已存在且内容不同，应作为新副本导入或明确选择替换，不能默默覆盖。更换电脑时携带 `.jpp` 即可，无需原来的缓存目录。

## 6. 识别与编辑的版本关系

每次重新识别生成新的 run；成功后保留旧 run 和当前修订谱。新结果先提供预览，用户明确选择“用新识别结果开始修订”时才建立新的编辑主谱。

工作台只有一张当前谱。谱面编辑直接写入主谱；手工 BPM / 拍号用于显式全曲重排，旧主谱保存为修订版本。识别参数和当前谱在同一保存快照内，没有跨阶段覆盖问题。

重新选另一首 MP3 默认创建新工程。若明确替换现有工程音频，必须保留原修订并说明其音频时间映射失效，不能沿用旧 `sourceTime` 假装仍能准确定位。

有来源的音符保存原始音频映射：`原曲时间 = run.clipStart + note.sourceTime`。新增的人工音符可能没有来源时间，不能编造对照定位。谱面播放采用编辑后的节奏；原曲定位采用来源时间，两种时间不混用。

## 7. 工程状态恢复

- 已识别完成：载入原曲、人声、结果和当前修订谱，恢复显示，无需重新识别。
- 已导入但未识别：载入原曲和片段设置，继续识别。
- 浏览器关闭、后端进程仍在处理：重新打开时重新关联工程任务，显示真实进度。
- 服务重启使模型任务中断：标记为“处理已中断”，保留原曲和之前已成功的识别版本，不伪造处理中状态。
- 当前未完成任务需要重新识别，尚不支持复用中途完成的人声阶段。只有整次任务成功后，其片段、人声和结果才登记到工程，避免把部分 WAV 当作完整产物。
- 正在一次模型推理内部中断：第一版不承诺恢复内部计算进度，重跑这一阶段，不能把部分 WAV 标成完整产物。

播放器恢复保存的播放位置，但不自动发声。原曲位置使用整首原曲秒数，人声位置使用识别片段秒数，分别保存。

## 8. 技术实现及修改点

继续使用现有 Node HTTP、Python 和原生 JavaScript/SVG，不需要为此引入 React 或云数据库。

| 层 | 新增/修改职责 |
| --- | --- |
| 工程文件模块 | `project-store.mjs` 管理目录、清单、资产、原子写入、导入/导出 |
| 工程 API | `/api/projects` 的新建、列表、读取、状态保存、资产播放和工程包导入/导出 |
| 首页控制器 | `project-controller.js` 统一当前工程、版本、保存队列、步骤切换、最近工程 |
| 识别处理器 | 任务属于工程/run，阶段完成后登记产物；成功后保存完整产物 |
| 识别视图 | 从工程读取数据和参数，刷新可恢复；不再以页面内存作为唯一状态 |
| 编辑视图 | 编辑器输出带 project ID 的当前谱修改；从工程恢复，不再打开临时 job 路径作为工程身份 |
| 对照播放器 | 原曲、人声、当前谱共享工程来源及选区信息 |

目前只保留一个工作视图 iframe 作为主页工程栏与工作区之间的边界，编辑组件直接存在于识别谱面内；不是第二个页面或嵌套编辑 iframe。消息协议统一。每条状态消息带 `projectId`、视图会话 ID 和 `revision`；切换工程后迟到的消息直接拒绝。谱面已经合并：工程保存请求只向一个工作区取完整快照。

后端按工程串行写入；版本不一致返回冲突，不使用最后到达的请求覆盖新修改。多个浏览器打开同一工程时提示冲突，第一版不做协同编辑。

写盘使用临时文件→原子替换，manifest 在完整资产写入后更新。导出拿固定 revision 的快照，而不是一边编辑一边打包移动中的目录。重开时以最后完整版本为准，恢复临时文件只在校验成功后进行。

ZIP 导入先解包到暂存目录，限制压缩后/解压后总量、文件数量及资产类型，拒绝越界路径和符号链接，校验 JSON、谱面及资产大小/哈希后再登记工程。导出与音频下载流式处理，避免把整首歌的多个 WAV 同时堆在浏览器内存。

ZIP 采用 Python 标准库 `zipfile`，没有增加第三方归档插件。工程保存改造不改变现有模型的科研用途授权限制。

## 9. 实施顺序和验收

1. 工程数据模型、磁盘工作副本、最近工程和统一工程栏，先贯通纯乐谱新建/保存/打开。
2. 原曲导入、识别任务归属、产物登记，识别视图能从磁盘恢复。
3. 编辑谱回写同一工程，切换阶段不丢修改；共享原曲/人声试听。
4. 完整 `.jpp` 导出与导入、另存为和版本一致性；将中断任务标记为可重新识别；阶段断点重用待后续实现。

必须通过的验收：

- 导入真实 MP3 → 识别 → 修改音符和歌词 → 保存工程 → 关闭页面及重启服务 → 打开工程，所有音频可试听，参数和修改保持一致。
- 把导出包放到另一个空的工作目录，不复制旧 `.audio-jobs` 或浏览器草稿，仍能恢复；不需要模型即可试听已保存的人声与谱。
- 识别成果原地编辑，保存重开不重新量化覆盖人工修订；再次识别失败也不损坏已有结果。
- 在处理中关闭页面可重新关联；服务中断后正确显示中断，并保留原曲和之前成功版本。
- 大文件、保存失败、损坏工程包、版本冲突不会生成假成功或覆盖另一工程。
- 浏览器不支持系统文件选择器时，工程包下载/重新上传的流程能完整往返。

关键验收不是“恢复几个输入框”，而是：**重新打开后不用重新选择原曲、不用重复分离，能听回原曲和人声，并继续修改上次那份简谱。**
