# 听歌记谱 Demo

上传 MP3 → 分离人声 → 从人声提取单条旋律 → 估计时值 → 预览简谱 → 人工核对 → 保存 `.jpu`。

这是可运行的本机处理 Demo，不是任意歌曲的准确转录承诺。混音入口只对分离的人声取音高；分离失败不回退到混音取音高。人声中的背景和声、合唱和伴奏泄漏仍可能误导音高跟踪。

## 启动和使用

本机已建立 `.venv-audio` 并下载人声模型。**原来的开发服务器需要重启一次**，才会加载新增音频接口：在运行 `npm run dev` 的终端按 Ctrl+C，再执行 `npm run dev`。

打开 `http://127.0.0.1:5173/transcribe.html`（若启动终端显示其他端口，使用那个端口）。编辑器“示例”菜单也有入口。

1. 选择歌曲 MP3，保留「歌曲原曲 · 先分离人声」。
2. 输入有人声的开始秒数，先识别 15–30 秒，再尝试长片段。最多处理 100MB 文件、10 分钟音频；同一时间一个任务。
3. 点「识别主旋律」。首先听提取的人声，确认没有把明显伴奏听成旋律；再试听识别旋律。
4. 核对速度 BPM、调号、拍号和第一音拍位，修改后直接重排，不重新跑分离。
5. 下载 `.jpu`，或点「到编辑器修订」。编辑器使用独立文件路径和草稿，不覆盖正在编辑的其他乐谱。选中音符后可在属性面板修改升降号。

「清唱／独奏／已提取的主旋律」仅用于没有伴奏的输入，它会跳过分离。页面另有人工合成的八音 MP3 流程样例；它不代表对带伴奏歌曲的准确率。

迁移到另一台机器，先运行 `npm run audio:setup`。需要 Python 3.12，模型第一次下载需要联网。准备完成后歌曲处理在本机进行，歌曲不上传第三方；文件和结果留在项目 `.audio-jobs/`，模型在 `.cache/torch/`，这两个目录及虚拟环境已加入忽略规则。

## 架构与方法

- 前端：原生 JavaScript、Web Audio、SVG；新页面 `transcribe.html`，复用现有简谱渲染器。
- 后端：原来的 Node HTTP 服务，上传、进度查询、取消任务、音频试听与乐谱接口；Python 子进程完成处理。没有增加另一个监听端口。
- 解码：项目内 FFmpeg，将所选片段解码成 44.1kHz 双声道 WAV。
- 分离：[Demucs](https://github.com/facebookresearch/demucs) `htdemucs` 的 vocals 声部；独立进程隔离模型资源。它分离人声声部，并不能保证只剩领唱。
- 音高：[librosa pYIN](https://librosa.org/doc/main/generated/librosa.pyin.html)，在 16kHz 人声上跟踪基频，保留原始起止秒数、MIDI 音高及稳定度。过滤无声、低稳定度和低人声能量帧；对颤音作短窗口稳定，起音检测分开重复音。
- 速度：混音的短时能量起音自相关，仅作为建议。这个 macOS 环境的原生 `beat_track` 在真实样本中出现进程崩溃，因此没有继续使用它。该估计可能有半速／倍速歧义，允许手动改 BPM。
- 排谱：按十六分音符网格量化，补休止、跨小节拆长音并加延音线；保留半音为升号，不能直接把半音舍入成自然音。当前仍受编辑器 2/4、4/4、200 小节和两组八度范围约束。

文件仍为 `jianpu-melody` 版本 2，新增可选 `accidental`（-1/0/1）和 `transcription` 来源元数据；识别音符保留 `pitchMidi`、`sourceTime`、`confidence`、`centsDeviation`。附加元数据不影响旧文件读取。原始 `result.json` 保存未量化的候选音符与音高时间轨迹，便于核对和重新排谱。

需核对标记表示算法稳定度不足或音高偏离，不是经过校准的识别准确率。前奏中没有人声的器乐旋律不会被这个入口记录；纯器乐歌曲应先人工提供主旋律声部。

## 本次验证及边界

- 人工生成八音 MP3：实际解码和 pYIN 输出 MIDI 60、62、64、65、67、69、71、72，生成 `1 2 3 4 | 5 6 7 高音1` 两小节，每音四分时值。
- Demucs 仓库测试音频：分离的人声能量很低，得到零个候选音符；没有用伴奏补音。
- [作者公开试听样本](https://ai.honu.io/papers/htdemucs/index.html)：The Easton Ellises — Falcon 69 的 20 秒混音片段，分离后得到 29 个候选音符。同片段参考人声用同一 pYIN 算法得到 51 个候选音符。301 个共同有音高采样点中，约 86.4% 的估计相差不到半个半音，差值中位数为零。**这是与另一条算法输出的相符程度，不是人工真值准确率；音符数量差异也显示了漏音、分段差异。** 外部音频只保留在测试缓存中。
- 实际浏览器上传→Python→SVG→试听→下载→转入编辑器、取消、损坏音频、手机布局由 `scripts/verify-transcribe.mjs` 验证；页面请求转交真实 API 和文件，没有启动开发服务器。

复测命令：

```sh
node --test tests/transcription.test.js tests/model.test.js tests/song.test.js tests/workbench.test.js
node scripts/verify-transcribe.mjs
```

浏览器检查需要 Playwright 和 Chrome，使用既有 Codex 本地运行时，也可指定 `PLAYWRIGHT_MODULE`。带主唱样本检查额外需要本次测试缓存音频，并设置 `TRANSCRIBE_TEST_MIXED=1`。

## 下一步提高质量

先用你要处理的实际歌曲，人工标注一段 20–30 秒主旋律，分开统计音高错误、漏音、伴奏误入和节奏错误。根据错误位置调整分离模型和主唱跟踪，再增加真正的拍点／小节起点推断、三连音与更细时值。合唱和领唱重叠时，需要领唱专门分离／多基频跟踪后再选择声部；只更换普通音高检测器不能解决声部身份问题。
